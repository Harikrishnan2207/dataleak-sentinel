# DataLeak Sentinel

**An Intelligent Database System for Detecting Unauthorized Bulk Data Extraction**

A lightweight database-security monitoring demo. It stores simulated user access logs in SQLite, scores every access with a transparent rule-based engine, and raises alerts when the pattern looks like bulk data extraction.

> **Synthetic data only.** All users, departments and access events are generated by the built-in simulator. DataLeak Sentinel does **not** connect to, read from or monitor any real production database, and it makes no claims about real-world detection accuracy.

## Features

| Area | What it does |
|---|---|
| Dashboard | KPI cards (total attempts, normal, suspicious, flagged users, high-risk events), activity trend, risk distribution, records-vs-threshold scatter, top users, recent alerts |
| User Activity | Searchable, filterable table: user ID, username, department, timestamp, access type, records, risk score, risk level, reason |
| Security Alerts | Alert list (username, timestamp, records, score, reason, review status), flagged-user summary, mark alerts as reviewed, CSV export |
| Audit Logs | Every access and detection result stored in SQLite, with source and query text; survives restarts; CSV export |
| Detection Rules | Edit thresholds and behaviour rules, then re-scan all stored logs |
| Query Console | Run a read-only SELECT as a simulated user against a synthetic customers table; the monitor counts the rows actually returned, scores them, raises alerts and logs the query |
| Demo Simulation | Generate normal / medium / bulk / repeated / burst activity, clear and regenerate, run a guided 7-step scenario, or log a single access of your own |

## Detection logic

Volume tiers (configurable, defaults shown):

| Records per access | Risk |
|---|---|
| 1 to 20 | Low |
| 21 to 100 | Medium |
| Above 100 | High |

Behaviour rules (all configurable):

- **Repeated high-volume access**: 3 or more accesses of at least 50 records within 60 minutes (+15 points).
- **Unusual access frequency**: 10 or more accesses within 15 minutes, even if each is small (+10 points).
- **Cumulative volume**: 500 or more records by one user within 60 minutes (+10 points).
- **Unusual for this user**: an access far larger than that user's own history (+15 points). It uses a robust z-score of the record count against the user's median (log scale, median absolute deviation as spread), needs at least 15 earlier accesses, and ignores accesses under 10 records. This is a statistical rule, not machine learning.

Each access gets a score from 0 to 100: volume sets a base score (Low 1 to 25, Medium 26 to 60, High 61 to 85), behaviour rules add points, and any triggered behaviour rule guarantees at least Medium. Scores of 26 or more raise an alert with the reasons listed. These are simple heuristics, not a trained model. The default thresholds, including the anomaly settings, were tuned on synthetic data only and would need recalibrating on real workloads.

## Installation (Windows)

Requires Python 3.10 or newer.

```powershell
cd dataleak-sentinel
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

If PowerShell blocks activation, run `Set-ExecutionPolicy -Scope Process Bypass` first, or use Command Prompt.

macOS or Linux: `source .venv/bin/activate` instead of the activate line above.

## Run

```powershell
streamlit run app.py
```

The app opens at http://localhost:8501. Open **Demo Simulation** and click **Generate demo data** (or use the button on the empty Dashboard).

The database is created automatically at `data/dataleak_sentinel.db`. To use a different file, set the `DATALEAK_DB_PATH` environment variable before starting.

## Run the tests

```powershell
python -m unittest discover -s tests -t . -v
```

The suite covers the volume boundaries, the behaviour rules, SQLite persistence and migration of older databases, alert review status, the guided scenario, the query gateway (measured row counts, rejected statements, timeouts) and a headless run of every page.

## Database tables

`access_logs` (every access), `detections` (score, level and reason per access), `alerts` (Medium and High detections) and `settings` (saved rule thresholds).

## Limitations

- Rule-based plus one statistical rule (per-user baseline): no peer-group comparison and no machine learning. A patient insider who raises their volume slowly can drag their own baseline upward. On steady synthetic users the rule catches a 19-row spike about 78% of the time and never flags accesses under 10 rows; these figures come from synthetic data.
- Batch and guided-scenario events use record counts chosen by the simulator. Only Query Console events are measured from real query results, and only for the synthetic customers table.
- Only queries sent through the Query Console are monitored. User identities are simulated (no login), and monitoring is by rows returned, so an aggregate such as COUNT(*) scores as harmless.
- Rejected queries (writes, multiple statements) are refused but not logged.
- Alert review is a simple New or Reviewed flag, with no ticketing workflow.
